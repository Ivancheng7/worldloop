> 状态：v0.2，2026-11-26（v0.1 的交互模型数据因导出器 bug 作废并全量重跑；记忆指标已改为相对地板归一化）

---

## 一句话

开源了一套**闭环 + 解析真值**的交互式世界模型评测：用 CC0 全景图构造可控相机轨迹，
把解析计算出来的真值光流当作标尺，测四件事——**动作是否被跟随**、**转一圈回来还是不是
同一个世界**、**物体离屏后还在不在**、**换一个动作会不会真的分叉**——并且给出单卡
16GB 上的实测时延与显存。

## 为什么现在做这个

1. 2026 年的世界模型综述盘点了 130 个评测（2018–2026），其中 74 个和"控制/交互"有关，
   **只有 6 个做闭环**（模型输出回灌成下一步输入），**没有一个测"回到之前看过的地方，
   世界是不是还是那个世界"**。而这恰恰是世界模型和视频生成器的分水岭。
2. 现有的动作评测（WorldMark、WBench）判分依赖**参考视频**或**付费 API 裁判**，复现性差；
   物理评测（Physics-IQ、PhyGenBench）依赖昂贵的人工标注。
3. 我们换了个思路：**旋转相机的透视视图是全景图的解析函数**，所以"真值光流""回访视图"
   "遮挡区间"都能直接算出来，不需要任何标注、不需要参考视频、不需要裁判模型。

## 我做了什么

### 1) 评测集：25 个 case，5 种协议，全部可复现

| 协议 | 脚本 | 时长 | 测什么 |
|---|---|---|---|
| `loop360` | 向右转 3×2s（60°/s） | 6s | 转满 360°，回到起点还是不是同一个场景 |
| `occlusion` | 右转 2s → 静止 2s → 左转 2s | 6s | 3 个探针区域离屏 4s 后是否还原 |
| `null_action` | 静止 4s | 4s | 世界静止时会不会自己动（运动地板） |
| `drift` | 连续右转 18s | 18s | 长时漂移速率 |
| `counterfactual` | 静止 2s →（左转/右转/静止）2s → 回转 2s | 6s | 分支是否真的由动作决定（`cf_action_sep` / `cf_null_drift`） |

场景用 Poly Haven 的 CC0 全景图（`abandoned_bakery`、`empty_warehouse` 等 6 张室内/街景），
每个 case 的起始朝向按 `i×47°` 轮换，避免挑图。

### 2) 真值：解析光流，零标注

对纯旋转相机，给定 `(yaw, pitch, fov)` 就能把全景图重投影成任意视角，因此
`frame1(p) = frame0(p + flow(p))` 里的 `flow` 可以**闭式解**出来。自检脚本 `tests/test_pano.py`
验证了两件事：把 frame0 用解析 flow warp 过去，和真渲染的 frame1 平均像素误差 7.3/255；
投影/反投影往返误差 0.000 px。

### 3) 指标

| 维度 | 指标 | 需要参考视频吗 |
|---|---|---|
| 动作保真 | `flow_cos`（预测光流 vs 解析光流的余弦）、`flow_mag_ratio`、`axis_purity`、`switch_latency` | 否（对解析真值） |
| 记忆/回访 | `revisit_dino`、`revisit_ssim`、`revisit_lpips`、`permanence_dino`、`drift_slope`，以及各自的**相对地板归一化版**（`*_norm`，评分用它） | 否（自身回访 + 自身负样本） |
| 静止稳定性 | `null_motion_px`（静止动作下的运动地板） | 否 |
| 因果 | `cf_action_sep`（动作支与静止支的分歧，↑）、`cf_null_drift`（静止支自身的漂移，↓） | 否（配对自身） |
| 成本 | 每 chunk 墙钟、realtime factor、显存峰值 | — |

### 4) 适配器（同一个接口，五种"世界"）

`oracle`（解析渲染器，上界）、`static`（永远不动的退化基线）、`wan2.1_t2v_1.3b`（无动作条件的
视频生成器，负对照）、`yume_5b`（5B 交互式世界模型，本机 16GB）、`matrix_game_3_5`（位姿条件，
走官方 HF Space）。

### 5) 校准（这是我认为最重要的一步）

先把"完美世界模型"（解析渲染器）跑一遍全流程，确认指标能拿满分：
`flow_cos = 0.998`、`revisit_dino = 1.000`、`revisit_ssim = 0.989`、`permanence = 0.988`、
`drift ≈ 0`、`null_motion = 0.023 px`、`cf_action_sep = 0.263`、`cf_null_drift = 0.000`，
World Score **97.2**。**如果这一步不是满分，后面所有比较都没有意义。**
过程中它帮我抓出六个会让结论完全反过来的 bug（见下）。

另外用 4 张**没参与核心集**的全景图（`hotel_room`、`lebombo`、`venice_sunset`、
`modern_buildings`，15 个 case）做了一次 OOD 校准：解析渲染器 96.9（比核心集低 0.3）、
Static 地板从 Control 5.7 涨到 13.5。后者不是模型变好了，而是 OOD 集没有 `drift` 这个
零光流 case（会把核心集 Control 均值拉低），加上夜景/户外的 RAFT 伪流更多。
**结论写进文档：跨 OOD 与核心集比较 Control，10 分以内的差异不算证据。**

交互式模型也跑了同一套 OOD（15/15），结果反而是这轮最有价值的一段：**它的 OOD
revisit SSIM 是 0.622，室内只有 0.400，看上去"出分布记得更牢"——但它的 OOD 相似度地板
是 0.572，室内是 0.363。** 也就是说涨的完全是地板：户外/夜景图更平滑、纹理更少，
"什么和什么都像"。扣掉地板后室内 0.070 / OOD 0.103，Memory 5.1 → 6.6 而不是 31.4 → 38.7。
这是整份材料里最清楚的一个例子：**同一个模型、同一套协议，Memory 能凭空跳 18 分，
而那 18 分来自图像统计，不来自记忆。**

## 结果（v0.2，2026-11-25/26，单卡 RTX 5060 Ti 16GB）

覆盖：Yume **4 个场景 × 3 协议 + 1 个 drift + 2 组反事实 = 19 个 case**（另有 15 个 OOD case）；Wan **4 场景 × 3 协议 + 1 组反事实 = 12 个 case**；两个非学习基线核心集 25 + OOD 15 全跑。
`±` 是按协议内 case 重采样 2000 次的 bootstrap 标准差（95% 区间约为 ±1.96×；
Causality 只有 2–6 个 group，重采样没有意义，只报点估计）。

**核心集（in-distribution）**

| 系统 | 是什么 | n | Control | Memory | Stability | Causality | **World Score** |
|---|---|---|---|---|---|---|---|
| `oracle_sim` | 解析渲染器（上界/校准） | 25 | 95.8 ± 0.2 | 98.7 | 94.1 | 100 | **97.2 ± 0.1** |
| `static` | 永远不动的退化基线 | 25 | 5.7 ± 1.1 | 98.7 | 99.9 | 0.0 | **23.7 ± 2.2** |
| `yume_5b` | 5B 交互式世界模型（本机真跑） | 19 | 78.0 ± 3.5 | 5.1 | 0.0 | 26.8 | **20.0 ± 3.2** |
| `wan2.1_t2v_1.3b` | 1.3B 文生视频（无动作输入） | 12 | 27.5 ± 3.1 | 3.9 | 76.1 | 0.0 | **10.3 ± 2.0** |

**OOD 校准集（4 张未参与核心集的全景图）**

| 系统 | n | Control | Memory | Stability | Causality | **World Score** |
|---|---|---|---|---|---|---|
| `oracle_sim_ood` | 15 | 95.8 ± 0.9 | 98.0 | 92.3 | 100 | **96.9 ± 0.5** |
| `static_ood` | 15 | 13.5 ± 0.6 | 98.0 | 99.8 | 0.0 | **36.3 ± 0.8** |
| `yume_5b_ood` | 15 | 76.4 ± 3.6 | 6.6 | 0.0 | 54.7 | **22.5 ± 3.3** |

`World Score = sqrt(Control × Memory)`：一个世界模型必须**听得懂动作**且**记得住世界**。
几何平均就是用来卡住两种退化解——"什么都不做"（Control 0）和"每 2 秒重新编一个世界"（Memory ≈ 0）。
注意 Yume 现在的 World Score **低于** static（20.0 vs 23.7）：这不是说冻结帧更有用
（它作为环境显然没用），而是说"会转但什么都不保留"和"保留一切但不动"在乘积上是同一个量级的失败，
乘积本来就不该拿来找更细的排序。

**八条主要发现**

1. **方向对、增益按场景错**：Yume 的动作方向一致度 **0.969**（整圈 0.995 / 回看 0.915）——
   转的方向没问题。但增益逐场景差很多：流量幅值比 0.70 / 0.80 / 0.90 / **1.33**，
   指令 360° 的整圈实际积分出 298° / 271° / 398° / **559°** 偏航。有个场景它转了两倍远，
   看起来"很听话"，实际上走过了两个世界。方向和增益必须分开评，合并成一个"动作跟随度"
   会把这个完美藏起来。
2. **转一圈就丢世界**：回访 SSIM **0.400**、DINO **0.352**（解析渲染器 0.989 / 1.000）。
   定性图更直观：6 秒后它在一个"看起来合理的房间"里，但不是原来那个房间。
   逐场景 revisit DINO 从 0.058 到 0.324——失败不均匀，这就是聚合要带 ± 的原因。
3. **原始记忆指标量的是"平滑度"不是"记忆"（指标已重做）**：回访相似度有一个随数据变化的地板——
   平滑、低纹理的画面跟什么都像。用模型**自己的**非回访帧对（起点视角 vs 被指令转到 120° 以外的帧）
   做地板，Yume 的 revisit DINO 0.352 对地板 **0.350**、revisit SSIM 0.400 对 0.363、
   permanence 0.191 对 **0.190**。也就是说它"回到原地"的那一帧，跟起点视角的相似度
   **正好等于**跟随便另一个方向的相似度：原始数字报的是它的画面统计，不是它的记忆。
   减去地板后 Memory 从 31.4 变成 **5.1**。这和废掉的 ASR 是同一类错误：分母/基线随数据变，
   却当成绝对量在平均。
4. **看开 4 秒比转一圈更致命**：扣掉地板后 permanence 0.018 < revisit DINO 0.066。
   物体一出画就没了，不存在"渐变退化"。
5. **它不会静止**：静止动作下画面仍以 **25.6 px/帧** 移动（解析渲染器 0.023，即 RAFT 噪声；Wan 1.12）。
   逐场景 10.5 / 37.5 / 34.8 / 19.6 px/帧，偏航最多积分到 **+93.9°**（指令 0°）。
   一个无法表示"没有变化"的世界模型，没法当策略的训练环境——策略的 no-op 会变成动作。
6. **反事实是最干净的判别器（指标已重做）**：同一个起点、同一个 seed，左转/右转/静止三条分支，
   测两个量——动作支与静止支的分歧 `cf_action_sep`（解析渲染器 0.263 / Yume 0.212 / Wan **0.000**），
   以及静止支自身的漂移 `cf_null_drift`（0.000 / 0.540 / **0.957**）。
   两者相乘成 Causality，得到 100 / 26.8 / 0。
   **为什么不再用旧的 ASR**：`post/pre` 的分母对确定性模型合法为 0，oracle 自己三对 ASR
   = 189.8/314.3/132.8 全被 100 截断，于是"oracle 97 vs Yume 95"这个看起来最漂亮的对比
   纯粹是 cap 伪影，两者不可区分。旧值改名 `ASR (legacy)` 只留审计，不进任何评分。
7. **代价**：Yume 生成 2 秒视频要 **190 秒**（0.011× 实时，约 90 倍慢于实时），
   18 秒的 drift episode 用了 1889 秒；显存 allocated 峰值 13.6GB。Wan 每 chunk 快约 2 倍、
   但仍慢 37 倍。所谓"16GB 能跑"是指装得下，不是能交互。
8. **导出器 bug 能让榜单变成谎话，现在它藏不住了**：v0.1 那批 Yume 帧有 buffer 复用 bug——
   每个 episode 在第一个 chunk 边界冻结 7 帧，然后回放自己开头的帧。这个 bug **会让分数变好看**：
   冻结的是真实渲染图，保真度指标几乎不动，反而让模型显得"更稳"（null motion 11.8 而不是 25.6）。
   抓它的方式不是看分数而是哈希帧：四个独立生成的 case 里有一帧逐字节相同。
   现在每个 case 都带 `frame_integrity`（`dup_frames` / `max_identical_run` / `rewound_frames` /
   `rewound_motion_deg`），`score` 在"相机还在动却重复帧"时打 WARNING。
   v0.1 的 Yume 数字全部作废，上表是 19 个 case 的干净重跑（另有 15 个 OOD case 重跑），
   每个 case 的 `rewound_frames` 都是 0。

## 七个值得讲的工程坑

1. **RAFT 的光流符号/网格约定**：torchvision 的 RAFT 返回的是"第 0 帧网格上的前向流"，
   而我第一版解析 flow 是"第 1 帧网格上的后向流"，两者差一个负号。oracle 的 `flow_cos`
   直接是 **−0.997**——看起来像"模型完全反向运动"，其实是基准自己错了。修法是改算
   `rotation_flow_forward`（在 cam0 网格上前向投影）。
2. **回访参考帧对齐**：第一版拿"模型自己生成的第 0 帧"当回访参考，但第 0 帧已经比条件帧
   多转了一步（7.5°），于是 oracle 的 `revisit_ssim` 只有 0.24。正确做法是拿**条件帧**
   当参考——回访发生在条件帧的位姿上，完美模型必须复现它。
3. **比值型指标会整体失效，不是"有个边界情况"**：`ASR = post/pre` 的分母对确定性模型
   合法为 0，`post/max(pre,1e-3)` 直接爆到 215110，封顶 100 之后 oracle 和 Yume 都是 95+，
   **这个维度就再也分不出好坏**——而它恰好是整个 benchmark 的核心卖点。
   换成两个有物理尺度的量（动作支与静止支的分歧、静止支自身漂移）再相乘，
   才是"敏感 + 特异"的 AND 语义。
4. **相似度型指标有随数据变化的地板，当绝对量用等于在量平滑度**：这是和第 3 条同一类的错误，
   只是更隐蔽——`revisit_ssim = 0.622` 看着比 `0.400` 好得多，但前者对应的"两张无关图"地板
   是 0.572、后者是 0.363，扣掉地板后是 0.103 对 0.070。**同一个模型、同一套协议，
   OOD 与核心集之间能凭空差 18 分，差的全是图像统计（户外/夜景更平滑、纹理更少），
   不是记忆。** 更极端的是 Yume 核心集的 `revisit_ssim = 0.400` 比它自己的地板 0.497 还低：
   它"转一圈回到原地"的那一帧，比随便挑一张无关的图还更不像起点。
   修法是给每个记忆指标同时算一个"负样本对"地板（起点视角 vs 相机被指令转到 120° 以外的帧；
   permanence 则用探针 A 对探针 B 的方向），评分改用 `(raw − floor)/(1 − floor)`。
   冻结帧没有自己的负样本对（画面不随指令变），回退到全景图 180° 处的解析渲染——
   这样它的记忆得高分、失败仍然留在 Control 轴上。
5. **相机基向量被镜像**（最致命的一个）：全景重投影用的是 `r = f × up`，这会让图像
   水平翻转——此时"相机向右转"在画面里表现为内容向右移，而任何正常模型被要求
   "pan right"都会让内容向左移。结果就是：**一个完全正确的模型会拿到 `flow_cos ≈ −1`**，
   榜单会把它判成"反向运动"。修法是改成右手系 `r = up × f`，并在 `tests/test_pano.py`
   里加了一条断言：右转 7.5° 时画面内容平均位移必须 < −10 px（现在实测 −51.9 px）。
   这个 bug 是 MG-3.5 adapter 的作者在核对 npz 位姿约定时发现的——也说明了
   "同一套几何有多处实现时必须有交叉验证"。
6. **导出器 buffer 复用，让 15 个 case 静默作废**：`continue_from_last=True` 时模型侧会把
   "16 帧静态头 + 上一 chunk" prepend 到输出，捕获 hook 必须切掉尾部 `chunk_frames` 只留新帧；
   修之前每个 episode 在第 17 帧冻结 7 帧、再把开头 8 帧回放一遍。
   抓法是给每帧做 md5 并检测"帧重复 + 相机仍在动"，而不是看榜单——因为这种 bug 抬分不降分。
7. **显存泄漏伪装成 CUDA 访问冲突**：上一轮跑完的 `yume_cli.py --serve` 守护进程不会自己退出，
   占着 10.2GB；下一轮再起一个 5B 服务，16GB 装不下，报错是
   `exited unexpectedly (code=3221225477)`（0xC0000005 access violation），
   完全指向错误方向。现在 adapter 启动前检查空闲显存、列出残留 PID 并给出清理命令。

## 局限（写在 README 里，面试也主动说）

- **只有旋转**，没有平移 → 评不了物理/接触；这是为了在 16GB 上可跑做的取舍。
- 720p / 8fps；6 个核心场景 + 4 个 OOD 场景，样本量小（定位是"协议可信"，不是"榜单权威"）。
  Yume 跑了 19/25 个核心 case + 15/15 个 OOD case，Wan 12/25（未跑 OOD），
  每行都标了 n 和 bootstrap 标准差。
- 探针是图像区域，不是实例分割。
- `switch_latency` 只来自 counterfactual 协议（只有它的动作在 episode 中途变化），
  所以 Control 的这一分量建立在很小的 n 上。
- Causality 的尺度常数 0.25 是用"两张不同全景之间的 DINO 距离 0.79"标定的，是校准值不是物理单位，
  数据集里最接近的一对只有 0.61。
- **记忆地板是模型相关的**：它用模型自己在 120° 以外的帧来量，所以"一转身就编一个新房间"的模型
  地板高、归一化反而低。这是有意的读法（连起点视角都不共享的世界本来也谈不上记得），
  但它确实把"没有记忆"和"世界不一致"混在了一起，是这条指标目前最大的解释风险。
- 大模型（Matrix-Game 3.5 ≥40GB、HY-WorldPlay ≥28GB、LingBot 8 卡）跑不了本机，
  榜单里会明确写"未评测及原因"，不装作评过。

## 下一步

1. 加 VLM judge 做"这个画面里少了个什么"的语义归因，和确定性指标交叉验证——
   现在的 `cf_action_sep` 只能回答"分支变了没有"，回答不了"变对了没有"；
   记忆地板也只能说"不像起点"，说不出"少了哪把椅子"。
2. 接位姿条件的模型（Matrix-Game 3.5 / LingBot-World），把"纯旋转"扩展到"平移+遮挡"——
   纯旋转的世界模型只要记住一张 360° 图就够了，平移才真正逼它建 3D。
3. 把评测和"世界模型当环境用"接起来：用同一套 case 测下游策略排序（world model as evaluator），
   检验"World Score 高的模型是不是真的训出更好的策略"。
